<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client form → members table | Parent-entered member data crosses into the DB (RLS-scoped) |
| acting-as chip → mutation attribution | Chip selection changes which member future actions attribute to |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-09 | Tampering | member create/edit/delete | mitigate | All writes go through useUpsertMember/useDeleteMember under the user's anon JWT; members RLS (initial_schema.sql) scopes INSERT/UPDATE to family_id = current_family_id() and DELETE to parents only |
| T-02-10 | Spoofing | AvatarChipRow visibility | mitigate | Chip row returns null for non-parent role (Open Q5); only a parent can switch acting-as context |
| T-02-11 | Information Disclosure | visible_sections filter | accept | visible_sections is a client-side nav convenience, not a security control; RLS remains the data boundary. A child hiding/showing a tab cannot read another family's data. |
</threat_model>
